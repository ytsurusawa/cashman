# 法務とコンプライアンス

営業メールを送る事業なので、ここを外すと事業ごと止まる。
**以下は実務上の整理であり、法的助言ではない。**
本格稼働の前に、弁護士または所轄官庁に確認すること。

---

## 特定電子メール法

### 原則はオプトイン（事前同意）

特定電子メールの送信適正化法は、**あらかじめ同意した相手にしか広告メールを送れない**
ことを原則としている（法3条1項）。

### ただし B2B の公表アドレスは適用除外

法3条1項4号により、**「自己の電子メールアドレスを公表している団体、または営業を営む個人」**
宛ての送信は、事前同意なしに行える。

つまり、

| 宛先 | 可否 |
|---|---|
| 会社サイトに公開されている `info@` `contact@` `sales@` | **送ってよい** |
| 採用ページに公開されている `recruit@` `hr@` | **送ってよい** |
| 名刺交換で得た個人アドレス | 同意があれば可 |
| **推測した個人アドレス**（`yamada@`） | **送らない** |
| 公表されていないアドレス | **送らない** |
| **個人（非事業者）のアドレス** | **送らない** |

`src/cashman/prospects.py` の `is_public_address()` がこの線引きをコードで持つ。
代表アドレスとみなせるローカルパート（`info` `contact` `sales` `recruit` 等）以外は
`is_public=0` となり、`sendable()` の対象から自動的に外れる。

**注意: 「公表されている」ことの確認は自動化しきれない。**
実務では、リスト化のときに「そのアドレスが会社サイトのどこに載っているか」の
URLを控えておくこと。後から指摘されたときに示せるのは、それだけ。

### 表示義務（法4条）

送信するメールには、以下の表示が必須。

| 必要な表示 | 実装場所 |
|---|---|
| 送信者の氏名または名称 | `compose.SenderIdentity.footer()` |
| 受信拒否の通知ができる旨 | 同上 |
| 受信拒否の通知先（メールアドレス等） | 同上 |
| 送信者の住所 | 同上 |
| 苦情・問い合わせの受付先 | 同上 |

すべてのメールにフッタが付くことを `tests/test_cashman.py::TestLegalFooter` が検証している。
**住所は必須なので、自宅住所を出したくない場合はバーチャルオフィスを契約すること**
（月1,000〜5,000円）。

### 受信拒否後の再送は明確な違反（法3条3項）

停止の意思を受け取ったら、以後一切送ってはいけない。

`src/cashman/sender.py::record_reply()` が返信を分類し、
停止の意思を検出したら**ドメイン単位で**配信停止に登録する。
アドレス単位ではなくドメイン単位で止めるのは、同じ会社の別部署に送る事故を防ぐため。

停止処理は4つのテストで守られている。

```
tests/test_cashman.py::TestSuppression::test_suppressed_email_is_never_drafted
tests/test_cashman.py::TestSuppression::test_domain_level_suppression_blocks_all_addresses
tests/test_cashman.py::TestSuppression::test_suppressed_draft_is_not_sent
tests/test_cashman.py::TestSuppression::test_optout_reply_suppresses_domain
```

自動分類は完璧ではないので、**週1回は返信を目視で確認**し、
取りこぼした停止依頼を `python3 -m cashman suppress <アドレス>` で手動登録すること。

### 罰則

措置命令に従わない場合、個人は1年以下の拘禁刑または100万円以下の罰金、
法人は3,000万円以下の罰金。**事業が止まる規模の制裁**である。

## 個人情報保護法

### 取得するデータの整理

| データ | 個人情報か | 扱い |
|---|---|---|
| 会社名・法人番号・代表アドレス | 該当しない | 制限なし |
| 担当者の氏名・個人アドレス | **該当する** | 利用目的の公表が必要 |
| 顧客から預かる業務データ | **該当する場合がある** | 委託先としての安全管理義務 |

### 必要な対応

1. **プライバシーポリシーをLPに掲載する。** 取得する情報と利用目的を書く。
2. **顧客の業務データを扱う場合、委託契約に安全管理措置を明記する。**
   受注処理の自動化では顧客の取引先情報を扱うことになるので、これは必須。
3. **保管場所と保管期間を決める。** 契約終了後に削除する手順まで決めておく。

### 特に注意すべき点

**顧客の業務データをLLM APIに送る場合、その旨の同意が要る。**
商談の時点で「処理にあたり外部のAIサービスを利用します」と明示し、
契約書に記載すること。後から発覚すると信用を失う。

API提供者が**入力データを学習に使わない**設定になっているかも確認する。
主要な事業者向けAPIは既定で学習に使わないが、契約上明示されているかを見ておく。

## スクレイピングとリスト取得

| 行為 | 判断 |
|---|---|
| 公開ページの閲覧・手動でのコピー | 通常は問題ない |
| 利用規約でスクレイピングを禁じているサイトからの自動取得 | **やらない** |
| `robots.txt` で拒否されているパスの自動取得 | **やらない** |
| 過度なアクセスでサーバに負荷をかける | **やらない**（偽計業務妨害となりうる） |
| 法人番号公表サイトのWeb-API | 公式APIなので問題ない |

**実務上、1日40通しか送らないのでリストは1日40〜60社あれば足りる。**
手動収集でも1時間で集まる量なので、規約が曖昧なサイトを無理に自動化する意味はない。
リスクに対してリターンが釣り合わない。

## 契約書

最低限、次の2本を用意する。ひな形は中小企業庁や各種公的機関が公開しているものを基礎にし、
**初回の1本だけは専門家にレビューしてもらう**（5〜10万円）。以降は使い回せる。

| 契約書 | 内容 |
|---|---|
| 業務委託基本契約書 | 契約期間・解約条件・秘密保持・再委託・責任範囲・データの取扱い |
| 個別契約書（発注書） | 対象業務・納期・金額・検収条件 |

### 必ず入れる条項

- **責任の上限**: 損害賠償の上限を「受領済みの委託料の範囲」に限定する。
  これが無いと、自動化の不具合で発生した損害を青天井で負う。
- **解約予告期間**: 1ヶ月前の書面通知。突然の解約でMRRが崩れるのを防ぐ。
- **データの返還・削除**: 契約終了時の扱いを明記する。
- **外部AIサービスの利用**: 上述のとおり明示する。

## インボイスと税務

| 項目 | 内容 |
|---|---|
| インボイス登録 | **B2B相手なら必須**。未登録だと相手が仕入税額控除できず、実質値引きを求められる |
| 消費税 | 登録すれば課税事業者。2割特例の適用可否を確認する |
| 会計ソフト | freee / マネーフォワード等。月額2,000円程度 |
| 税理士 | 月商80万円を超えたあたりで契約（月2〜3万円） |
| 副業と本業 | **就業規則の副業規定を必ず確認する。** ここが最大のリスク要因になりうる |

**最後の項目は事業を始める前に確認すること。**
副業禁止規定に抵触したまま進めると、事業が軌道に乗った時点で本業を失うか、
事業を畳むかの選択を迫られる。
